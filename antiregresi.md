## 1. `[Semua Modul]` Firestore Rules & Query — pola `get()` cross-document

**1.1.** Kalau security rule butuh baca dokumen lain lewat `get()` (misalnya cek `kelasAmpu` dari `users/{uid}` untuk memvalidasi akses), DAN query dari klien **tidak** menyertakan `where()` yang cocok dengan field yang dicek rule tersebut, Firestore akan **menolak SELURUH query** dengan `Missing or insufficient permissions` — bukan menyaring hasil per dokumen secara diam-diam.

> **Kejadian nyata**: ini yang mendasari kenapa `getSiswaList()`, `getRiwayatSetoran()`, `getMenulisLog()` di `assets/firestore-data.js` (Tahsin-Tahfizh) semuanya WAJIB dikasih parameter `kelas`/`scope` eksplisit, bukan cuma `siswaId`. Konsekuensinya: kalau menambah query baru ke koleksi mana pun yang rule-nya pakai `get()`, pastikan klien selalu kasih `where()` yang sama sebelum dianggap selesai.

**1.2.** `allow get:` dan `allow list:` bisa dipisah dari `allow read:` gabungan. Berguna kalau butuh kondisi berbeda untuk baca-satu-dokumen vs baca-daftar (contoh: koleksi `users` — admin boleh `list` semua permintaan akun orang tua lewat kondisi konstan `allow list: if isAdmin();`, tanpa kena masalah §1.1 karena kondisinya tidak bergantung `resource.data`).

**1.3.** Kalau menambah collection/query Firestore baru untuk fitur apa pun, **selalu cek dulu**: apakah rule-nya butuh `get()` cross-document? Kalau iya, pastikan query klien sudah dibatasi field yang sama.

## 4. `[Tahsin-Tahfizh]` Kompatibilitas Mundur Skema Data

**4.1.** Koleksi `menulis_log` punya 2 generasi skema yang HARUS tetap didukung bersamaan (tidak ada migrasi data, entri lama dibiarkan apa adanya):
- **Lama (flat)**: `jilidIqro`, `halamanMulai`, `halamanAkhir` di level atas dokumen.
- **Baru (nested)**: `materi` (object dengan `tipe: 'iqro' | 'quran'`) dan `penilaian` (object, hanya untuk `tipe === 'quran'`).

**4.2. Aturan wajib**: setiap halaman yang MEMBACA `menulis_log` (saat ini: `riwayat-siswa.html`, `riwayat-anak.html`, `cetak-laporan.html`, dan `catat-menulis.html` sendiri untuk riwayat ringkas) HARUS punya fallback: kalau `r.materi` tidak ada, jatuh balik ke field flat lama. Pola helper yang dipakai (duplikasi disengaja per halaman, karena tidak ada shared JS antar file HTML selain modul `assets/*.js`):

```js
function menulisPosisiLabel(r) {
  if (!r) return '-';
  if (r.materi?.tipe === 'quran') return r.materi.label;
  if (r.materi?.tipe === 'iqro') return `Iqro ${r.materi.jilidIqro} — Hal. ...`;
  return `${r.jilidIqro ? `Iqro ${r.jilidIqro} — ` : ''}Halaman ${r.halamanMulai}...`; // fallback lama
}
```

**4.3.** Pola ini berlaku umum: **kalau menambah field baru ke koleksi yang sudah dipakai/punya data produksi**, jangan mengganti/menghapus field lama kecuali sudah ada rencana migrasi data eksplisit yang disepakati. Tambah field baru secara aditif, dan pastikan semua pembaca data lama tetap bisa menampilkan entri tanpa field baru itu tanpa error atau tampilan rusak (`undefined`, dsb).

**4.4. Kejadian nyata yang hampir terlewat**: saat menambah field `materi`/`penilaian` ke `menulis_log`, awalnya hanya `catat-menulis.html` (form input) dan `riwayat-siswa.html` (riwayat guru) yang terpikir untuk diubah. Baru setelah `grep -rn "halamanAkhir\|jilidIqro" --include="*.html"` dijalankan ke seluruh repo, ketahuan `riwayat-anak.html` (portal orang tua) dan `cetak-laporan.html` (laporan cetak) **juga** membaca field-field itu secara langsung dan akan tampil rusak untuk mayoritas siswa (kelas 3-6, jenjang Al-Qur'an) kalau tidak ikut diubah.

**4.5. Aturan wajib turunan**: sebelum menganggap perubahan skema/field pada koleksi Firestore manapun selesai, jalankan pencarian menyeluruh (`grep -rn` nama field/koleksi ke seluruh repo, bukan cuma folder modul sendiri) untuk memastikan semua konsumen data itu sudah tertangani.

## 5. `[Tahsin-Tahfizh]` Fitur Edit — Batasan Kepemilikan & Field

**5.1.** Entri `setoran` dan `menulis_log` hanya boleh diedit/dihapus oleh pembuatnya sendiri (`createdBy == request.auth.uid`), dijaga di `firestore.rules`, bukan cuma disembunyikan di UI. Field `siswaId`, `kelas`, `createdBy` dikunci di rule `allow update` (tidak boleh berubah lewat operasi update) supaya kepemilikan/atribusi tidak bisa dipindah diam-diam.

**5.2.** Untuk `setoran` khususnya: field materi/Baca & Tandai (`materi`, `detailAyat`, `detailBacaanIqro`) **sengaja tidak dibuka untuk diedit** — hanya `jenis`, `statusHafalan`, `catatan`. Kalau materi yang salah input, alurnya hapus & input ulang, bukan edit, supaya histori bacaan (dasar perhitungan progres surah) tetap konsisten. Jangan buka field materi untuk edit di masa depan tanpa mendiskusikan dampaknya ke logika progres terlebih dahulu.

## 6. `[Semua Modul]` Sanity Check Sebelum Mengirim File Hasil Edit

**6.1.** Untuk file HTML/JS yang diedit signifikan (bukan perubahan satu-dua baris), selalu jalankan pengecekan sederhana sebelum dianggap selesai:
- Keseimbangan `{`/`}` dan `(`/`)` (mis. `content.count('{') - content.count('}')` harus 0).
- Untuk file dengan `<script type="module">`, ekstrak isi script dan jalankan `node --check` untuk memastikan sintaks JS valid.
- Untuk perubahan CSS di file bersama, jalankan diff terhadap versi sebelumnya dan pastikan hanya baris yang dimaksud yang berubah (murni aditif kalau memang niatnya begitu).

## 7. `[Semua Modul]` Prinsip Umum Arsitektur — Jangan Dilanggar Tanpa Diskusi

**7.1.** Tidak ada framework, tidak ada build step. Semua halaman HTML statis + `<script type="module">` inline, import modul ES langsung dari `assets/*.js` dan CDN (`gstatic.com/firebasejs`). Kalau ada dorongan menambah bundler/framework, itu perubahan arsitektur besar — diskusikan dulu dengan pemilik proyek, jangan langsung dikerjakan.

**7.2.** `DEMO_MODE` di `assets/firebase.js` (aktif otomatis kalau `firebaseConfig.apiKey` masih placeholder) harus tetap dipertahankan di semua fungsi data layer (`firestore-data.js`, `firestore-data-akademik.js`), walau config asli sudah terpasang dan DEMO_MODE tidak aktif di produksi — ini penting untuk development/preview tanpa koneksi backend.

**7.3.** Pola kerja dengan pemilik proyek: **tidak ada akses push langsung ke repo** dari sesi AI mana pun. Alurnya selalu: kirim file yang berubah (dengan path repo-relative persis, dizip kalau lebih dari satu file) → pemilik proyek menimpa manual ke repo lokal → commit & push dilakukan pemilik proyek sendiri. Konsekuensi: **jangan pernah asumsikan perubahan sudah "live"** hanya karena sudah dikirim — selalu anggap perlu konfirmasi eksplisit bahwa file sudah dideploy sebelum membangun fitur lanjutan di atasnya.

**8.4. Skema Firestore baru (per 2026-09-04).**
- `tp_kktp` — field baru `bobotMapel` (number, default 1 kalau kosong = bobot rata). Dipakai `hitungNilaiAkhirMapel()`. **BUKAN persen, bukan wajib total 100** — angka bebas dibandingkan relatif antar TP dalam mapel yang sama.
- `nilai_tp` — sekarang **khusus SLM**. Field `sas` lama di dokumen existing dibiarkan menggantung (TIDAK dihapus, TIDAK dibaca lagi) — kompatibilitas mundur murni pasif, tidak perlu migrasi karena belum ada data SAS produksi saat perubahan ini dibuat (dikonfirmasi ke pemilik sistem).
- `asesmen_cakupan/{id}` *(baru)* — 1 dokumen per (mapel, kelas, semester, tahunAjaran, **jenis**: `'sts'|'sas'`), berisi `tpIds: string[]`. Cakupan STS dan SAS untuk mapel+kelas yang SAMA sengaja terpisah total, tidak ada logika "copy dari STS ke SAS" atau sebaliknya.
- `nilai_sts/{id}` & `nilai_sas/{id}` *(baru)* — nilai murni per (tpId, siswaId, mapel, kelas, semester, tahunAjaran), field `nilai`. Fungsi baca/tulisnya di `firestore-data-akademik.js` **generik lewat parameter `jenis`** (nama koleksi ditentukan lookup `KOLEKSI_NILAI_ASESMEN[jenis]`) — kalau menambah jenis asesmen baru serupa di masa depan, ikuti pola generik ini, jangan duplikasi fungsi.
- `firestore.rules` — ketiga koleksi baru di atas pakai rule persis pola `nilai_tp` (`bolehMapelKelas()`), sudah ditambahkan.

**8.5. Formula nilai akhir (rapor resmi).**
```
efektifSLM(tp, siswa) = STS > SLM pada TP itu?  → pakai STS
                                                 → pakai SLM asli
nilaiAkhirTP  = SAS kosong pada TP itu?  → efektifSLM saja
                                          → efektifSLM × bobotSlm% + SAS × bobotSas%
nilaiAkhirMapel = rata-rata TERTIMBANG nilaiAkhirTP semua TP, bobot = tp.bobotMapel (default 1)
```
STS yang TIDAK lebih tinggi dari SLM tidak berpengaruh sama sekali ke nilai akhir — hanya tersimpan untuk rapor bayangan STS (belum dibangun). Implementasi ada di `hitungNilaiAkhirTP(nilaiSlm, nilaiSas, tp, nilaiSts)` dan `hitungNilaiAkhirMapel(entriesPerTP)` di `firestore-data-akademik.js` — **jangan hitung ulang formula ini secara manual di halaman baru manapun**, selalu impor & pakai kedua fungsi ini supaya rumus rapor tidak pernah punya 2 sumber kebenaran yang bisa berbeda hasil.

**8.6. Pola back-button kondisional per role.** Halaman yang bisa diakses admin *dan* guru/wali lewat jalur berbeda (`setup-tp.html`, `absensi.html`, `kelola-dpl.html`, `proyek-stem.html`) simpan `session` sebagai variabel scope-modul (`let session = null;` di luar `onAuthChange`, diisi `session = s;` di dalamnya), lalu tombol kembali baca variabel itu:

Kalau menambah halaman baru yang diakses lebih dari satu jalur, ikuti pola ini — jangan hardcode satu tujuan kembali saja.

**8.7. Setup TP di-dedupe per (mapel, tingkatan), BUKAN per (mapel, kelas).** TP & KKTP berlaku per tingkatan (kelas paralel 4A/4B pakai TP yang sama), beda dari SLM/STS/SAS yang memang per kelas. `setup-tp-hub.html` men-dedupe `session.penugasan` (yang berbentuk `{mapel, kelas}`) jadi pasangan unik `{mapel, tingkatan}` sebelum ditampilkan sebagai kartu — kalau lupa dedupe ini, guru yang mengampu mapel sama di 2 kelas paralel akan lihat kartu Setup TP dobel untuk TP yang sebenarnya sama.

**8.8. Kejadian nyata — sisa teks salah tempel saat menyalin halaman via `sed`.** Membangun SAS dan Kokurikuler dengan menyalin struktur STS lewat `sed` (mengganti kata kunci "STS"→"SAS" dst.) dua kali menghasilkan bug nyata yang baru ketahuan lewat audit grep, bukan saat menulis:
- `nilai-sas-cakupan-hub.html`: 2 baris teks UI masih menyebut "STS" walau sudah jadi halaman SAS.
- `kokurikuler-hub.html` (disalin dari `nilai-sts-hub.html`, bukan sekadar sed kata "STS"→"Kokurikuler"): **guard akses ikut salah tersalin** — awalnya memeriksa `session.penugasan` (punya guru mapel) padahal Kokurikuler itu fitur wali kelas yang seharusnya memeriksa `session.waliKelas`. Kalau tidak ketahuan, wali kelas yang bukan guru mapel manapun akan selalu melihat halaman kosong "Belum ada penugasan", padahal harusnya bisa akses.
- **Aturan wajib turunan**: setelah menyalin halaman dengan `sed`/copy-paste sebagai basis halaman baru, WAJIB `grep -n` nama fitur asal (case-sensitive, termasuk singkatan) ke file hasil salinan, DAN baca ulang bagian guard akses (`session.role`, `session.penugasan` vs `session.waliKelas`) secara eksplisit — sed yang mengganti teks tampilan tidak menjamin logika kondisional ikut benar secara semantik.

**8.9. Prinsip beranda tipis.** `beranda.html` (dan landing hub lain di bawahnya seperti `nilai-hub.html`/`wali-hub.html`) TIDAK melakukan query Firestore per-item untuk menghitung status lengkap/belum — cukup hitung ringkasan dari `session` (`penugasan.length`, `waliKelas.length`, dsb.) yang sudah tersedia tanpa fetch tambahan. Query yang lebih detail (status "X/Y TP terisi", dsb.) baru dilakukan di hub selanjutnya yang lebih spesifik, saat kartu itu benar-benar dibuka. Kalau ada dorongan menambah status detail langsung di `beranda.html` lagi di masa depan, ingat ini yang menyebabkan versi lama lambat dimuat untuk guru dengan banyak penugasan.

**8.10. Rapor itu lintas-mapel per siswa — bukan skop guru-mapel.** `nilai-sts-hub.html` dkk skopnya per guru (cuma mapel yang diampu), tapi Rapor butuh SEMUA mapel sekaligus untuk satu siswa — yang punya pandangan itu cuma wali kelas. Karena itu **Rapor STS ditaruh di `wali-hub.html`, bukan di `nilai-sts-hub.html`**, walau secara nama fitur terasa lebih dekat ke STS. Kalau menambah "Rapor SAS" nanti, ikuti pola yang sama — masuk `wali-hub.html`, bukan `nilai-sas-hub.html`.

**8.11. Mekanisme cetak: pola v1 (jendela baru + `@page`), BUKAN pola `@media print` `cetak-laporan.html`.** Ada dua pola cetak berbeda di repo ini — jangan disamaratakan:
- **Pola lama** (`cetak-laporan.html` Tahsin-Tahfizh): toggle `display` lewat `@media print` DI HALAMAN YANG SAMA (`#reportOutput`/`.no-print` di `assets/style.css`). Tidak dapat running footer otomatis per halaman, tidak dapat nomor halaman, dan berbagi dokumen dengan CSS `phone-shell`/`app-header` yang berisiko ikut ke hasil cetak.
- **Pola baru** (`rapor-sts-cetak.html`, diadopsi dari `rapor/preview.html` aplikasi v1): tombol Cetak membangun HTML rapor sebagai string, buka `window.open('', '_blank', ...)`, `w.document.write(fullHTML)` — dokumen BARU yang sepenuhnya independen dari app shell, dengan `<style>` sendiri termasuk:
  ```css
  @page{
    size: A4; margin: 1.5cm;
    @bottom-left{ content: "Kelas X | Nama | NISN"; ... }
    @bottom-right{ content: "Halaman " counter(page) " dari " counter(pages); ... }
  }
  tr{page-break-inside:avoid}
  thead{display:table-header-group}
  .rpr-ttd-wrap{page-break-inside:avoid}
  ```
  Ini yang membuat tabel tidak terpotong sembarangan dan footer+nomor halaman muncul otomatis di SETIAP halaman fisik tanpa kita perlu tahu di muka jadi berapa halaman. **Pakai pola ini (bukan pola lama) untuk setiap halaman cetak/rapor baru** — termasuk nanti Rapor SAS dan rapor resmi akhir semester. Fungsi pembangun HTML isi rapor (`buildBodyPrint()`) sengaja dipakai dua kali (pratinjau di layar DAN sumber cetak sungguhan) supaya pratinjau tidak pernah beda dari hasil cetak asli.

**BATASAN PENTING — kenapa "cetak semua siswa sekelas sekaligus" TIDAK dibangun:** `@page{ @bottom-left/@bottom-right }` cuma bisa punya SATU isi statis untuk SELURUH dokumen cetak, tidak bisa "footer ganti otomatis per siswa" kalau satu dokumen cetak berisi banyak siswa sekaligus (mis. loop 1 kelas). Ada teknik `@page` bernama (properti CSS `page: namahalaman` per elemen + `@page namahalaman{...}` per kelompok) yang secara spesifikasi CSS Paged Media Level 3 bisa mengatasi ini, TAPI dukungan browser (khususnya Chrome/Chromium yang dipakai guru untuk "Simpan sebagai PDF") belum cukup matang/konsisten untuk dipertaruhkan pada dokumen resmi seperti rapor — risikonya halaman tercetak kehilangan identitas siswa yang benar kalau lembarnya tercecer, dan itu baru ketahuan setelah dicetak, bukan saat development. **Keputusan final (2026-09-04, disetujui pemilik proyek): rapor tetap satu-siswa-per-cetak selamanya untuk fitur ini** — jangan diusulkan ulang kecuali ada perubahan nyata pada dukungan CSS Paged Media browser target.

**8.12. Skema NISN — field baru terpisah dari NIS, sengaja pakai `updateDoc` bukan `batch.set()`.** Koleksi `siswa` (dipakai bareng Tahsin-Tahfizh) sebelumnya cuma punya `nis` (nomor lokal sekolah). Rapor formal wajib mencantumkan **NISN** (Nomor Induk Siswa Nasional, 10 digit, berbeda dari NIS) — field baru `nisn`, diisi lewat `kelola-nisn.html` (`saveNisnBatch()` di `firestore-data-akademik.js`). **PENTING**: fungsi ini pakai `batch.update()` per siswa (cuma menyentuh field `nisn`), BUKAN `batch.set()` seperti `seed-siswa.html` — `seed-siswa.html` men-*overwrite* seluruh dokumen dari array hardcode-nya, jadi TIDAK BOLEH dipakai ulang untuk mengisi NISN (berisiko menimpa field lain yang sudah berubah sejak seed awal, termasuk field yang dipakai Tahsin-Tahfizh). NISN semua siswa existing (403 siswa) **masih kosong** per 2026-09-04 — tidak ada sumber data yang bisa dipakai mengisi otomatis, harus diisi manual oleh admin per kelas.

**8.13. Keterbatasan nama Wali Kelas di tanda tangan rapor.** Tidak ada struktur data "daftar nama wali kelas per kelas" yang terpisah dari akun login — nama yang tercetak di kolom tanda tangan "Wali Kelas" pada `rapor-sts-cetak.html` diambil dari `session.nama` (akun yang sedang login saat mencetak). Ini benar selama yang mencetak memang wali kelas ybs sendiri, tapi keliru kalau admin mencetak atas nama wali kelas lain — untuk kasus itu, nama perlu diedit manual di hasil cetak sebelum ditandatangani. Kalau nanti dibutuhkan pencetakan massal lintas-akun (misal admin mencetak rapor semua kelas sekaligus), pertimbangkan menambah field `namaWali`/`nbmWali` ke struktur data kelas (belum ada tempatnya sekarang) alih-alih terus mengandalkan `session.nama`.

**8.14. Pola impor file Excel: SheetJS via `import()` dinamis, validasi NISN defensif thd leading-zero.** `import-nisn.html` adalah halaman PERTAMA di repo yang membaca file Excel dari sisi klien (bukan cuma menulis, seperti `seed-mapel.html`/`seed-siswa.html` yang isinya hardcode array). Dua hal penting kalau membuat halaman serupa di masa depan (mis. impor data lain dari Dapodik):
- **Library**: SheetJS dimuat lewat `import('https://cdn.jsdelivr.net/npm/xlsx@0.18.5/+esm')` di dalam handler event (bukan `<script src>` global di `<head>`) — konsisten dengan pola `firebase.js` yang juga pakai `import()` dinamis dari CDN gstatic, bukan tag script biasa. Jangan tambah `<script>` tag CDN kalau bisa pakai `import()` dinamis, supaya tidak menambah beban muat halaman lain yang tidak butuh library itu.
- **Parsing sel**: `sheet_to_json(sheet, {header:1, raw:false, defval:''})` — `raw:false` WAJIB dipakai untuk kolom berisi ID panjang (NISN/NIK/NIS) supaya SheetJS mengambil TEKS TERFORMAT apa adanya, bukan nilai numerik mentah yang berisiko dibulatkan/notasi-ilmiah kalau kolomnya kebetulan tersimpan sebagai angka di file sumber.
- **Validasi NISN 3-tingkat** (fungsi `validasiNisn()`): persis 10 digit → `ok`; kurang dari 10 digit tapi semua karakter angka → `dipad` (di-`padStart('0')` otomatis KARENA kemungkinan besar 0 di depan hilang, TAPI tetap ditandai visual kuning di UI, tidak didiamkan begitu saja); lebih dari 10 digit atau ada karakter non-digit → `invalid`, dikeluarkan dari proses simpan otomatis, wajib ditinjau manual. Prinsip ini ("auto-fix yang paling mungkin benar, TAPI selalu tampak & bisa dibatalkan admin sebelum commit ke database") berlaku umum untuk impor data massal apa pun di masa depan — jangan auto-fix secara diam-diam tanpa jejak visual.
- **Pencocokan baris file ke dokumen Firestore**: berdasarkan `nama` (dinormalisasi trim+uppercase+collapse-spasi) DAN `kelas` sekaligus (bukan nama saja — berisiko App kalau ada nama yang sama di kelas berbeda), diambil LIVE lewat `getSiswaByKelas()` per kelas yang benar-benar muncul di file (bukan query semua 15 kelas kalau file cuma sebagian). Baris yang tidak ketemu pasangannya WAJIB tampil sebagai "tidak ditemukan" dan default TIDAK tercentang — jangan pernah default-checked untuk baris yang pencocokannya tidak pasti.

## 10. `[Bersama]` Kelola Data Siswa (admin) & Ganti NIS (2026-09-10)

**10.1. Peta lengkap referensi `siswaId` — WAJIB dibaca ulang kalau ada koleksi baru yang menyimpan data per-siswa di masa depan.** NIS adalah Document ID koleksi `siswa`, tapi juga direferensikan sebagai field `siswaId` di **8 koleksi lain**: `setoran`, `menulis_log` (Tahsin-Tahfizh), `nilai_tp`, `nilai_sts`, `nilai_sas`, `absensi_rapor`, `kokurikuler`, `ekstrakurikuler_siswa` (Akademik) — plus array `anakIds` milik akun `users` berrole `orangtua`. Kalau membuat koleksi baru yang menyimpan nilai/catatan per siswa, **tambahkan ke daftar ini** (dan ke `gantiNis()` di `firestore-data-akademik.js`) — kalau lupa, siswa yang NIS-nya pernah diganti akan "kehilangan" riwayat di koleksi baru itu tanpa error yang kelihatan (query-nya tetap sukses, cuma hasilnya kosong karena `siswaId` sudah tidak cocok).

**10.2. Kenapa `setoran`/`menulis_log` butuh `|| isAdmin()` di rules, tapi 6 koleksi lain tidak.** Base rule `setoran`/`menulis_log` punya `allow update: if false` (sengaja immutable — riwayat setoran tidak boleh diedit diam-diam) DAN `allow delete` cuma untuk `createdBy == request.auth.uid` (pembuat asli, admin tidak termasuk). Kombinasi ini artinya sebelum sesi ini, **admin tidak punya jalan apa pun** untuk memindahkan `siswaId` di kedua koleksi itu. Ditambahkan `|| isAdmin()` di `create` dan `delete` (BUKAN di `update` — itu tetap `if false`, tidak diubah) khusus untuk alur salin-lalu-hapus di `gantiNis()`. 6 koleksi Akademik lainnya (`nilai_tp`/`sts`/`sas`, `absensi_rapor`, `kokurikuler`, `ekstrakurikuler_siswa`) rule update-nya SUDAH mengizinkan admin (`bolehMapelKelas`/`bolehWaliKelas` selalu OR dengan `myProfile().role=='admin'`), jadi `gantiNis()` cukup `updateDoc({siswaId: baru})` langsung, tanpa perlu ubah rules apa pun untuk 6 koleksi itu.

**10.3. Kalau menambah query list baru ke `nilai_tp`/`nilai_sts`/`nilai_sas`: WAJIB sertakan filter `mapel` DAN `kelas` sekaligus, tidak bisa salah satu saja.** Pola ini konsisten di SETIAP query list ke tiga koleksi itu di seluruh `firestore-data-akademik.js` (lihat §2 soal kenapa list query butuh filter eksplisit yang match rule). `gantiNis()` mengikuti pola ini dengan cara di-loop per mapel (`getMapelList()`) — bukan satu query longgar `siswaId+kelas` saja seperti 5 koleksi lain yang rule-nya cuma butuh `kelas` (`setoran`, `menulis_log`, `absensi_rapor`, `kokurikuler`, `ekstrakurikuler_siswa`).

**10.4. `gantiNis()` sengaja TIDAK atomik penuh, tapi idempoten.** Batch Firestore maksimal 500 operasi — siswa kelas 5-6 dengan riwayat setoran bertahun-tahun bisa melebihi itu untuk satu koleksi saja, jadi migrasi dipecah jadi banyak batch kecil (~450 operasi/chunk) berurutan, bukan satu transaksi besar. Kalau proses gagal di tengah jalan (mis. koneksi putus), dokumen `siswa` LAMA belum dihapus (dihapus PALING TERAKHIR, setelah semua koleksi lain sukses dipindah) sehingga aman dicoba ulang — tiap langkah query ulang "siapa yang masih pakai NIS lama", dokumen yang sudah pindah tidak diproses dua kali. **Jangan ubah urutan ini** (hapus siswa lama harus tetap paling akhir) kalau mengembangkan fungsi ini lebih lanjut.

**10.5. Tidak ada admin hub di sisi Tahsin-Tahfizh** — `kelola-siswa.html` ditaruh di `akademik/` (satu-satunya tempat admin hub nyata ada, `admin-hub.html`) walau datanya dipakai bersama. Kalau nanti Tahsin-Tahfizh dapat admin hub sendiri, pertimbangkan menambah link ke halaman ini dari sana juga (bukan menduplikasi halamannya).

## 11. `[Akademik]` Mutasi Siswa (usulan wali kelas → approve admin) (2026-09-10)

**11.1. NIS `-` (belum diketahui) TIDAK disimpan literal sebagai Document ID.** Kalau dua wali kelas kebetulan sama-sama mengusulkan siswa dengan NIS `-` berdekatan waktu, keduanya akan bertabrakan di ID yang sama persis. Sebagai gantinya: `setujuiMutasi()` men-generate NIS sementara unik (`sementara-xxxxxx`) lewat `buatNisSementara()`, disimpan dengan flag `nisSementara:true` di dokumen `siswa`. Admin **wajib** memfinalisasi lewat fitur **Ganti NIS** (§10) begitu bagian administrasi memberi NIS resmi — `gantiNis()` otomatis membersihkan flag ini (`nisSementara:false`) saat NIS diganti. `kelola-siswa.html` menampilkan badge merah "NIS Sementara" di kartu siswa supaya kelihatan jelas yang belum final.

**11.2. Rule `mutasi_siswa` SENGAJA tidak memakai pola `bolehWaliKelas(resource.data.kelas)` seperti koleksi lain.** Alasannya beda dari alasan di §10.2 — di sini soal LIST QUERY ADMIN, bukan soal update yang diblokir. Kalau rule pakai `bolehWaliKelas(resource.data.kelas)` (yang berisi `get()` ke profil user), maka mengikuti pola §2/§8.1 yang sudah terbukti di seluruh koleksi lain, Firestore akan MEWAJIBKAN query eksplisit filter `kelas` — padahal admin di `kelola-mutasi.html` justru butuh lihat SEMUA usulan LINTAS KELAS sekaligus (itu intinya jadi antrean terpusat). Solusinya: rule `mutasi_siswa` pakai kepemilikan lewat field `createdBy` biasa (`resource.data.createdBy == request.auth.uid`) — bukan `get()` — dikombinasi `isAdmin()` yang juga tidak bergantung pada `resource.data`. Karena TIDAK ADA cabang OR yang memakai `get()` bergantung pada field hasil query, list query aman TANPA filter tambahan, baik untuk admin (lihat semua) maupun wali kelas (query `where('createdBy','==',uid)` sendiri, cocok trivial dengan rule). **Pelajaran untuk koleksi baru di masa depan**: kalau butuh admin bisa list SEMUA dokumen lintas kelas/pemilik, JANGAN pakai `bolehKelas`/`bolehWaliKelas`/`bolehMapelKelas` (semuanya pakai `get()`) — pakai field `createdBy`/pemilik biasa + `isAdmin()` saja.

**11.3. Alur approve TIDAK memakai Cloud Function** — situs ini statis (lihat prinsip di README/HANDOFF), semua logika approve jalan di client `kelola-mutasi.html` yang memanggil `createSiswa()`/`updateSiswaData()` langsung dari `firestore-data-akademik.js` (sama seperti alur approve akun orang tua Tahsin-Tahfizh di `kelola-akun-ortu.html`). Ini berarti approve HANYA bisa terjadi kalau admin membuka halaman itu dan menekan tombol — tidak ada proses latar belakang otomatis.

**11.4. Jenjang Tahsin-Tahfizh (iqro/Al-Qur'an) untuk siswa hasil Mutasi Masuk di-default dari KELAS** (`/^[12]/.test(kelas)` → iqro, selain itu → quran) — wali kelas Akademik yang mengusulkan tidak diminta memilih jenjang karena belum tentu tahu. Guru Tahsin-Tahfizh/admin bisa mengoreksi lewat `kelola-siswa.html` kalau default itu salah untuk siswa tertentu.

**11.5. Skema `siswa` bertambah `tempatLahir` (string) dan `tanggalLahir` (string format `YYYY-MM-DD`, BUKAN Firestore Timestamp — supaya cocok langsung dengan `<input type="date">`.value tanpa konversi).** Ditambahkan di `createSiswa()`/`updateSiswaData()` dan form `kelola-siswa.html` sejak sesi ini — dokumen siswa LAMA (dibuat sebelum sesi ini) tidak punya field ini, akan tampil kosong di form edit (bukan error, `value="${escapeHtml(s.tempatLahir || '')}"` sudah menangani fallback).

## 12. `[Akademik]` Kelengkapan Rapor: Cover, Identitas Peserta Didik, Keterangan Pindah Sekolah (2026-09-12)

**12.1. Biodata 17-poin (Identitas Peserta Didik) SENGAJA disimpan di koleksi baru `identitas_siswa/{siswaId}` (Document ID = siswaId/NIS), BUKAN field tambahan di `siswa`.** Alasan: `siswa/{id}` rule-nya `allow write: if isAdmin()` (blanket, admin-only, sengaja begitu karena NIS adalah Document ID — lihat §10). Kalau biodata ini ditaruh di `siswa` juga, wali kelas TIDAK BISA ikut mengisi tanpa melonggarkan rule admin-only itu untuk field sensitif (nama/kelas/NIS/aktif) juga — trade-off yang tidak sepadan untuk data yang levelnya "deskriptif", bukan identitas inti. Dengan koleksi terpisah, rule `identitas_siswa` bisa mengizinkan wali kelas dari kelas yang sama TANPA menyentuh rule `siswa` sama sekali.

**12.2. Rule `identitas_siswa` memakai `get()` ke `siswa/{id}` untuk cek `bolehWaliKelas(kelas)` — ini AMAN, beda dari peringatan di §2/§8.1/§11.2.** Bedanya: akses ke `identitas_siswa` di seluruh UI (`kelengkapan-rapor.html`) SELALU lewat `getDoc`/`setDoc` dengan ID yang sudah diketahui (siswaId dari URL), TIDAK PERNAH lewat `list`/query. Tanpa pengaman ini, fungsi akan "memindahkan" riwayat siswa ke NIS yang SAMA (no-op tapi boros — setoran/menulis_log tetap kena copy+delete, cuma ganti doc ID auto-generate tanpa perlu), lalu di baris terakhir **menghapus satu-satunya dokumen siswa yang ada** — kehilangan data total untuk siswa itu. Pengaman ditaruh DI DALAM fungsi (bukan cuma di caller/data yang sudah difilter), karena fungsi ini reusable dan sesi mendatang bisa memanggilnya dengan data yang belum tentu sudah difilter dengan benar.

**16.4. Arah penggabungan: NIS BARU (Dapodik) yang dipertahankan, bukan NIS lama.** Keputusan disepakati bersama pemilik proyek — NIS Dapodik dianggap NIS resmi/NIPD yang seharusnya dipakai selamanya. Field `jenjang` (Iqro/Al-Qur'an), `tamatIqro` (kalau ada), dan `aktif` (kalau `false` di data lama) DIPERTAHANKAN dari dokumen lama — ditulis ke dokumen baru SEBELUM riwayat dipindah — supaya data yang sudah benar/manual dari guru Tahsin-Tahfizh tidak tertimpa nilai default. Riwayat di 8 koleksi (persis pola `gantiNis()` §10: `setoran`/`menulis_log` copy+delete karena rule `update:false`, 6 koleksi lain `updateDoc` biasa) + `anakIds` akun orang tua dipindah ke NIS baru, lalu dokumen NIS lama dihapus PALING TERAKHIR.

**16.5. Halaman eksekusi (`akademik/perbaiki-duplikat-siswa.html`) adalah utilitas SEKALI-JALAN dengan 355 pasangan tertanam langsung di kode** (bukan diketik ulang oleh admin, bukan diunggah lewat file — sudah pasti/tervalidasi dari §16.2). Tidak ditautkan dari navigasi manapun (beda dari fitur permanen) — diakses langsung lewat URL, dijalankan sekali, sesudahnya boleh dibiarkan atau dihapus. Idempoten: `gabungkanSiswaDuplikat()` mengecek dulu apakah dokumen NIS lama masih ada — kalau sudah tidak ada (karena proses sebelumnya berhasil atau halaman dijalankan dua kali), pasangan itu dilewati tanpa error, aman untuk retry kalau sesi browser terputus di tengah 355 pasangan.

**16.6. PELAJARAN UNTUK IMPOR MASSAL DI MASA DEPAN**: `praLihatImporSiswa()`/`jalankanImporSiswa()` (§13) mencocokkan SEMATA-MATA berdasarkan NIS persis — TIDAK ada pencocokan fallback berdasarkan nama kalau NIS berbeda. Ini sudah benar secara desain (NIS memang dimaksudkan sebagai kunci unik, mencocokkan berdasarkan nama akan rawan salah-cocok/terlalu longgar untuk fitur umum) — tapi kalau ke depannya ada sumber data (Dapodik atau lainnya) yang **PASTI** punya siswa yang sudah ada di sistem dengan NIS BERBEDA dari yang di file, **impor massal akan SELALU menganggapnya siswa baru dan menduplikasi** — bukan bug, tapi konsekuensi dari desain "NIS sebagai kunci". Kalau situasi ini terulang, pola di §16 (cocokkan nama+kelas offline, filter yang NIS-nya sudah sama, jalankan `gabungkanSiswaDuplikat()` massal) adalah cara **memperbaiki setelah kejadian** — bukan solusi untuk MENCEGAHNYA. Kalau ingin mencegah di masa depan, pertimbangkan menambah opsi "cocokkan juga berdasarkan nama+kelas kalau NIS tidak ketemu" di `praLihatImporSiswa()` sebagai peringatan (bukan auto-merge) sebelum admin menekan Proses Impor.

## 17. `[Akademik]` Perbaikan Kapitalisasi Nama akibat Impor Dapodik (2026-09-26)

**17.1. AKAR MASALAH: `jalankanImporSiswa()` (§13) dan `gabungkanSiswaDuplikat()` (§16) SELALU menulis field `nama` dari sumber Dapodik, bukan cuma untuk 355 pasangan yang digabung (§16), tapi untuk SEMUA baris impor (termasuk 48 yang NIS-nya sudah cocok dari awal, ditangani sebagai UPDATE biasa oleh `jalankanImporSiswa()`).** Karena sebagian data asli Dapodik ditulis HURUF BESAR SEMUA oleh operator sekolah asal (kesalahan input di sisi Dapodik, bukan bug sistem ini), sebagian nama siswa di `siswa` sekarang jadi ALL CAPS setelah impor — ditemukan pemilik proyek setelah §16 dijalankan.

**17.2. Perbaikan: `praLihatKapitalisasiNama()`/`terapkanKapitalisasiNama()` (baru, di `firestore-data-akademik.js`), dipakai halaman utilitas `akademik/perbaiki-kapitalisasi-nama.html`.** Beda dari §16 (355 pasangan tertanam langsung di kode, hasil pencocokan offline), perbaikan ini **memindai dinamis SELURUH koleksi `siswa`** (bukan daftar tertanam) — mencari nama yang sama persis dengan versi UPPERCASE-nya (regex `/[A-Za-z]/.test(s) && s === s.toUpperCase()`) lalu mengonversi ke Title Case. Dipilih dinamis (bukan daftar tertanam seperti §16) karena cakupannya BUKAN cuma 355 pasangan dari §16 — bisa juga kena 48 pasangan yang NIS-nya sudah cocok dari awal (§16.2) dan berpotensi siswa lain yang datanya diperbarui `jalankanImporSiswa()` di luar konteks §16.

**17.3. Konversi Title Case PER KATA (dipisah spasi), bukan per-huruf-setelah-tanda-baca.** Kalau pakai regex `\b` (word boundary) untuk menemukan huruf pertama tiap "kata", nama dengan apostrof seperti "Syafi'i"/"Qurrotu'aini" akan rusak (huruf setelah apostrof ikut dikapitalkan jadi "Syafi'I"). Solusi: `nama.split(/\s+/).map(w => huruf-pertama-besar + sisanya-kecil)` — cuma huruf pertama tiap token-dipisah-spasi yang dikapitalkan, sisa token (termasuk yang setelah apostrof/tanda hubung) selalu di-lowercase. Konsekuensinya: nama dengan tanda hubung dalam SATU token tanpa spasi (mis. "SITI-AMINAH" tanpa spasi di sekitar tanda hubung) akan jadi "Siti-aminah" (huruf setelah tanda hubung tetap kecil) — belum ditemukan kasus nyata di 403 data siswa saat ini, tapi kalau muncul di masa depan, halaman `perbaiki-kapitalisasi-nama.html` punya checkbox per-baris untuk mengecualikan baris yang hasil konversinya kurang tepat sebelum diterapkan.

**17.4. Deteksi "semua kapital" SENGAJA tidak menyentuh nama yang sudah campuran/benar** — kalau nama sudah punya minimal satu huruf kecil, tidak ikut terdeteksi. Ini bikin halaman aman dijalankan berulang kali (idempoten secara alami, beda dari §16 yang butuh pengecekan `nisLama===nisBaru` eksplisit) — nama yang sudah diperbaiki tidak akan terdeteksi lagi di pemindaian berikutnya.

**17.5. HANYA field `nama` yang ditulis** (lewat `writeBatch` langsung, bukan `updateSiswaData()` — supaya tidak melalui whitelist field itu untuk operasi sesederhana ini) — field lain (kelas, jenjang, aktif, NISN, dst) tidak disentuh sama sekali.

**17.6. Belum bisa diverifikasi end-to-end oleh Claude** (sama seperti §16 — tidak ada akses Firestore dari lingkungan kerja). Fairel perlu membuka `perbaiki-kapitalisasi-nama.html` langsung lewat URL (tidak ditautkan dari navigasi manapun, sama seperti §16.5), meninjau daftar sebelum-sesudah yang muncul, lalu menekan tombol terapkan.

## 19. `[Akademik]` Bobot TP dalam Mapel: dari Rasio Bebas jadi Persentase (2026-09-27)

**19.1. AKAR MASALAH: `tp_kktp.bobotMapel` sebelumnya adalah RASIO RELATIF BEBAS (bukan persen, tidak wajib total 100) — DISENGAJA sejak awal dibuat** (lihat komentar lama di `saveTP()`: *"supaya tambah/hapus TP di tengah semester tidak memaksa guru merapikan ulang bobot TP lain"*). Tapi di lapangan, guru (pemilik proyek sendiri) salah paham menganggapnya persen. Ini BUKAN cuma salah paham kosmetik — konsekuensinya bisa membalik makna angka yang diinput. Contoh nyata yang memicu perbaikan ini: guru mengisi 15 (bermaksud "15%") pada satu TP, sementara TP lain di mapel yang sama masih default (bobot 1). Karena `hitungNilaiAkhirMapel()` menghitung `bobot / totalBobot` (BUKAN `bobot / 100`), hasilnya BUKAN "TP ini dapat porsi kecil 15%" tapi **TP ini mendominasi 15/(15+1+1+1) ≈ 83%** — kebalikan total dari maksud guru. Rumus hitungnya SENDIRI tidak salah (rata-rata tertimbang yang benar secara matematis untuk RASIO apa pun) — yang salah adalah model mental input yang dipakai guru vs yang didesain sistem. Diputuskan (atas permintaan pemilik proyek): ganti total desain jadi PERSENTASE SUNGGUHAN, karena "lebih mudah dipahami" — walau ini berarti kenyamanan tambah/hapus TP tanpa merapikan ulang (alasan desain lama) dikorbankan; mitigasinya di §19.3.

**19.2. `hitungNilaiAkhirMapel()` TIDAK diubah rumusnya sama sekali** — tetap `Σ(nilai×bobot) / Σ(bobot)` dari entri yang valid. Ini PENTING dipahami: rumus ini SUDAH SELALU benar untuk rasio apa pun (tidak butuh totalnya = 100 untuk menghasilkan rata-rata tertimbang yang benar) — jadi migrasi ke persentase TIDAK mengubah SATU PUN nilai akhir mapel yang sudah pernah dihitung dari bobot lama, asal RASIO antar-TP dipertahankan (persis yang dilakukan `normalisasiPersenBobotMapel()` di §19.3, BUKAN di-set ulang sembarangan). Yang berubah HANYA cara angkanya diberi label/ditampilkan (dari rasio bebas jadi persen) dan cara divalidasi saat input (peringatan kalau total ≠ 100).

**19.3. `normalisasiPersenBobotMapel(tpList)` (fungsi murni, baru) + `terapkanNormalisasiBobotMapel(hasil)` (penulis batch, baru)** — mengonversi bobot lama (rasio bebas, biasanya default 1 untuk TP yang belum pernah disentuh) jadi persentase bulat yang tepat total 100, TANPA mengubah rasio (lihat §19.2). Pembulatan pakai metode **largest-remainder / Hare quota** (bagi eksak dulu, ambil lantai/floor semua, sisa pembulatan didistribusikan ke entri dengan sisa desimal terbesar) — supaya total SELALU tepat 100 meski dibulatkan ke bilangan bulat, bukan cuma "mendekati 100". Dipanggil lewat tombol **"Konversi ke Persentase"** di `setup-tp.html` (banner muncul otomatis kalau total bobot TP di mapel+tingkatan yang sedang dibuka ≠ 100, toleransi ±0.5) — SELALU butuh klik + konfirmasi eksplisit guru (menampilkan pratinjau before→after per TP di dialog konfirmasi), TIDAK PERNAH otomatis/silent, mengikuti pola `perbaiki-*.html` sebelumnya (§16/§17) walau ini bukan halaman terpisah, cuma tombol inline di halaman yang sudah ada.

**19.4. TIDAK ada validasi keras (hard block) yang memaksa total = 100 saat simpan satu TP** — cuma peringatan (`confirm()`) yang bisa dilewati. Ini SENGAJA (bukan lupa) — mempertahankan sebagian fleksibilitas desain lama (§19.1): guru tetap bisa menyimpan TP baru/edit satu-satu di tengah proses merapikan tanpa dipaksa menyelesaikan semuanya dalam satu kali simpan. Indikator live di form (`updateInfoBobotMapel()`, dihitung terhadap TP LAIN saja — mengecualikan TP yang sedang diedit sendiri lewat `editingId`, supaya tidak dihitung dobel) dan banner total di atas daftar TP (`renderTotalBobotBanner()`) yang jadi pengingat utama, bukan validasi keras.

**19.5. Default persentase saat "Tambah TP Baru" DIUBAH dari hardcoded `1` jadi saran dinamis**: kalau ini TP pertama di mapel+tingkatan itu → default 100 (satu-satunya TP, wajar penuh). Kalau sudah ada TP lain → default = `100 - totalBobotTPLain` (bisa 0 kalau sudah penuh) — mengarahkan guru ke total 100% sebagai titik awal, tapi tetap bisa diubah bebas sebelum simpan.

**19.6. Tampilan pill "Bobot mapel Nx" di `setup-tp.html`, `nilai-slm.html`, `nilai-sas-cakupan.html`, `nilai-sts-cakupan.html` diubah semua jadi "N% dari nilai mapel"** — halaman-halaman itu cuma menampilkan (read-only), tidak menghitung ulang apa pun, jadi tidak ada risiko regresi hitung dari perubahan label ini.

**19.7. TIDAK ada migrasi batch global otomatis untuk SEMUA mapel×tingkatan sekaligus** — disengaja: konversi terjadi per mapel+tingkatan, dipicu guru sendiri lewat tombol saat membuka `setup-tp.html` untuk mapel itu (banner akan selalu muncul untuk mapel yang belum pernah dikonversi, karena default lama bobot=1 per TP hampir pasti tidak total 100 kecuali kebetulan). Ini konsisten dengan pola sebelumnya (§16/§17) yang juga tidak memaksa migrasi serentak — tapi konsekuensinya: SEMUA ~12 mapel × 6 tingkatan yang punya TP akan menunjukkan banner "belum 100%" sampai masing-masing dibuka & dikonversi satu per satu oleh guru pengampu terkait. Kalau ini dirasa terlalu banyak langkah manual, pertimbangkan halaman migrasi batch terpisah (pola `perbaiki-*.html`) di sesi mendatang.

**19.8. Belum diuji ke Firestore sungguhan** (tidak ada akses jaringan Firebase dari lingkungan kerja, sama seperti §16-§18). Yang perlu ditinjau Fairel: buka `setup-tp.html` untuk mapel yang sebelumnya salah isi (yang memicu perbaikan ini), cek banner "belum 100%" muncul dengan angka yang masuk akal, coba "Konversi ke Persentase", pastikan hasil pratinjau before→after masuk akal, lalu cek nilai akhir mapel siswa terkait TIDAK berubah dibanding sebelum konversi (§19.2 seharusnya menjamin ini).
